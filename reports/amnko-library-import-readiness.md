# AMNKO HSE Library Import Readiness

## Scope and evidence

- Input crosswalk: `reports/amnko-library-content-crosswalk.csv`.
- Active source records: 487.
- Confirmed content paths: 348.
- Unresolved records intentionally left unlinked: 139.
- Confirmed evidence: exact equality between `dbo.tblLibrary.Rowguid` and the filename stem under `XOM/Library/`. Same-stem PDF/TXT entries are variants of one source record, not automatically separate documents.
- No source permissions were inferred from filename, path, or archive metadata.

## Current application storage and display contract

`app/actions/manage-documents.ts` defines `HSEDocument` and `getDocuments`.
A displayable target row requires, at minimum:

- `id` — stable target identifier generated by the approved migration, never guessed.
- `company_id` — the approved target company; the current read path filters by this value.
- `title`, `category`, `version`, `status`.
- `file_url`, `file_name`, `file_size`, `file_type`, and `blob_pathname` for download/display metadata.
- `folder_id` referencing `public.document_folder` when a verified folder mapping exists.
- `is_public` and `allowed_emails` only after an approved permission mapping.

`getDocuments` returns rows from `public.document`; admins see company/all rows, while regular users see only rows where `is_public=true` or their email is in `allowed_emails`. Folders are read from `public.document_folder` and scoped by active `company_membership`. Therefore inserting metadata without a valid company and visibility policy will not make documents appear correctly.

The existing upload flow uses Vercel Blob with public objects and path shape `hse-files/{companyId}/{timestamp}-{safeName}`. The migration must not invent Blob URLs or reuse this timestamp naming pattern as a source identity. Each imported object needs a deterministic, collision-checked pathname derived from the source Rowguid and verified filename, or an explicitly approved alternative.

## Selective archive retrieval feasibility

The 348 confirmed rows contain an `ArchivePath` in the crosswalk, and the original ZIP central directory provides each member's compressed/uncompressed metadata. A full archive download is not required in principle: a ZIP member can be retrieved selectively by byte ranges (local-header/data range, with the central-directory offsets) and decompressed locally, provided the original Google Drive download endpoint continues to support authenticated HTTP Range requests and the download authorization remains valid.

This has not been executed in this preparation phase. The central-directory-only evidence does not provide SHA-256, so each selected member must be streamed/decompressed during the approved transfer and hashed before upload. PDF/TXT same-stem variants must be treated under an explicit content policy: choose the canonical display file only after review, or preserve both with a verified variant relationship; do not silently create duplicate documents.

## Per-file readiness for the 348 confirmed rows

- Source identity: **ready** — `LibraryId`, `Rowguid`, source name, and archive member path are present in the crosswalk.
- Archive path: **ready** for the confirmed rows — `XOM/Library/{Rowguid}.{extension}`.
- Content bytes: **retrievable selectively in principle**, but not yet downloaded or integrity-verified.
- SHA-256: **missing** until the selected ZIP members are streamed.
- Target Blob URL/pathname: **missing by design**; must be created only during approved upload after hashing and collision checks.
- Target company ID: **missing**; must be explicitly supplied/verified before any target row is prepared.
- Target folder UUID: **missing**; `LibraryId/LibraryParentId` to `document_folder.id/parent_id` is not an approved UUID mapping.
- Permissions: **not ready**; `tblLibraryAccess` semantics and principals have not been proven equivalent to `is_public/allowed_emails`.
- Existing-target conflict status: **not checked against Neon** under the read-only restriction; execution must perform a target-side source-key/ledger lookup and stop on conflicts.

## Safe execution sequence after approval

1. Freeze and verify the crosswalk hash and the original Drive download authorization. Select only the 348 confirmed archive members; do not include the 139 unresolved rows or the separate incident/journey attachment paths.
2. Resolve and approve the target `company_id`, target schema constraints, source-key ledger columns/table, and folder mapping. Preserve `LibraryId`, `Rowguid`, source name, archive path, variant, and content hash in the ledger.
3. Resolve folder relationships before documents. Create or reuse folders only through deterministic source-key entries; stop on duplicate source keys, conflicting parentage, or an occupied target ID without authoritative ownership evidence.
4. For each selected member, retrieve only its ZIP byte ranges, decompress to a stream, validate filename/extension and byte count, compute SHA-256, and compare against the expected ZIP metadata. Do not upload on mismatch.
5. Upload to Blob with a deterministic source-derived pathname and no overwrite. Record the actual pathname/URL and hash in the same resumable ledger transaction as the document insert.
6. Insert/reuse `public.document` only when the source-key ledger confirms no duplicate and all required target fields are approved. Preserve existing rows; never replace or merge by title, date, or filename.
7. Apply only an approved ACL mapping. If permissions remain unproven, keep the row out of regular-user visibility and record it as pending ACL review rather than making it public.
8. Validate counts: 348 source rows selected, canonical document count according to the approved PDF/TXT variant policy, zero missing content for displayable rows, zero hash mismatches, no duplicate source keys, correct folder ancestry, and explicit exception lists for ACLs and the 139 unresolved rows.

## Required approvals/blockers

1. Approval to use the original Google Drive download endpoint with selective Range requests and to download only the confirmed ZIP members.
2. Explicit target `company_id` and read-only schema/constraint verification for `public.document` and `public.document_folder`.
3. Approved source-key ledger/idempotency design and write transaction boundaries.
4. Decision on whether PDF/TXT same-stem pairs are one canonical document plus searchable variant, or two separately visible documents.
5. Verified folder mapping from source hierarchy to target folders.
6. Reviewed interpretation and target principal mapping for `tblLibraryAccess`.
7. Separate authorization for Blob uploads and database writes, followed by a separate authorization for any unresolved-row work.

## Decision

**Yes, the 348 confirmed files can be moved without downloading the entire archive**, using selective ZIP member retrieval. The minimum step to move from preparation to execution is to approve the seven items above, starting with the Drive Range-download authorization, target company/schema and ledger design, and the PDF/TXT and folder/ACL policies. Until those approvals exist, no file should be extracted, uploaded, or represented by a guessed Blob URL, UUID, folder, or permission.
